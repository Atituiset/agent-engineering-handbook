# 06 · 代码评审与人机协作

[[toc]]

## 要点

- **瓶颈已经从「写」转移到「审」。** 不改评审方式，AI 的提效红利会被下游吃掉。
- **「有没有人读过代码」是不精确的代理指标**；真正的问题是「这次变更可能出什么错，哪道检查最适合抓住它」。
- **按风险分级评审**：高风险、难回滚的留给人；中风险自动检查 + 抽样；低风险自动化。
- **作者先自证**：不要把未经自己审查的 AI 代码甩给同事。
- **每段合并代码都必须有一个人负责**，且这个人理解它。
- **警惕认知债**：代码增长快于团队理解，长期会削弱你驾驭智能体的能力。

## 1. 瓶颈转移

Anthropic monorepo 每日落地变更从 2026 年 5 月约 2,500 增至 9 月 30,000 以上，团队不得不迁移到自研版本控制系统（[AN25](/sources/anthropic#an25)，厂商自报）。美团在 31 万行重构中遇到「木桶效应」：AI 极大压缩了编码时间，压力系统性地向下游 Code Review 集中（[CN01](/sources/chinese#cn01)）。Simon Willison 起初怀疑并行跑多个智能体，正是因为评审速度才是天然瓶颈（[PR03](/sources/practitioners#pr03)）。

## 2. 从「人读每一行」到「多层检查」

Claude Code 团队的做法是**多层而非单一闸门**（[AN19](/sources/anthropic#an19)，厂商自报）：

1. 作者先自证（运行、测试、附证据）。
2. 每个 PR 先过 AI 评审：多个智能体找 bug，另一组投票确认后才发布评论。
3. 可阻断的安全评审。
4. lint / 类型 / 测试 / 构建。
5. 按风险分级的人工审批。
6. 一键回滚。

> "We think 'did a human read the code?' is an imprecise proxy for 'what could go wrong with this change, and which check—automated or human—is the right one to catch it?'"

OpenAI 走得更远：人可以评审 PR 但不是必须的，几乎所有评审都已转为智能体之间进行（[OA01](/sources/openai#oa01)，厂商自报）。**注意**：这是在拥有非常严格的机械化架构约束（第 04 章）前提下的选择，不能脱离前提照搬。

## 3. 风险分级

Thoughtworks 雷达把「风险分级的人工监督」列为 Trial（[TW26](/sources/thoughtworks#tw26)），把「人在环中的表演」列为 Caution（[TW27](/sources/thoughtworks#tw27)）：以同样强度评审一切，最终会变成人批准自己实际上无法判断的东西，没人真正负责。

Böckeler 给出了三个评估维度（[TW16](/sources/thoughtworks#tw16)、[CN05](/sources/chinese#cn05)）：

- **概率**：出错的可能性多大？（新领域、复杂逻辑、模型不熟悉的 API → 高）
- **影响**：出错后果多严重？（支付、权限、数据迁移 → 高）
- **可检测性**：出错了能不能被发现？（有完善测试和监控 → 高可检测）

一个可操作的分级示例：

| 等级 | 典型变更 | 评审方式 |
| --- | --- | --- |
| 低 | 文档、测试补充、内部工具、样式 | 自动检查通过即可合并 |
| 中 | 常规业务功能、有测试覆盖的重构 | 自动检查 + AI 评审 + 抽样人工评审 |
| 高 | 认证授权、支付、数据迁移、公共 API、架构边界、安全敏感代码 | 前置方案评审 + 人工逐行评审 + 可回滚发布 |

GitHub 的建议与此一致：复杂、跨仓库、需要深厚领域知识或涉及生产关键/安全敏感逻辑的任务更适合人自己做（[BT14](/sources/bigtech#bt14)）。

## 4. 作者的责任

Simon Willison 把「把未经审查的代码强加给协作者」列为头号反模式（[PR12](/sources/practitioners#pr12)）：如果你提交了智能体产出的成百上千行代码却没确认它能工作，你就是把真正的工作转嫁给了评审者。好的 PR：

- 作者已确认能工作；
- 足够小，便于高效评审（几个小 PR 胜过一个大 PR）；
- 附带上下文与验证证据（手工测试记录、截图、视频）；
- PR 描述作者自己读过——智能体写的描述也要审。

美团的 **Pre-PR 机制**把这一点制度化：提交前开发者必须先用 AI 多轮自查，修复所有 AI 能发现的问题，再提交标准 PR 文档；人则重点把关前置的技术方案评审与业务逻辑（[CN01](/sources/chinese#cn01)）。

Greg Brockman 给 OpenAI 团队的要求：**确保每段合并的代码都有一个人负责**；评审标准不低于人写的代码；确保作者理解自己提交的内容（[X04](/sources/x-posts#x04)）。Addy Osmani 的个人原则是只合并自己理解了的代码（[PR27](/sources/practitioners#pr27)）。InfoQ 对谈中的一句话很直白：「Agent 只会道歉，没办法背锅。」（[CN07](/sources/chinese#cn07)）

## 5. 评审的焦点前移

美团的经验：评审的问题应该从「你写得对吗？」转变为「我们是否在正确的约束下解决正确的问题？」——AI 审查规范类问题并做业务逻辑初筛，人重点在前置技术方案评审环节把关（[CN01](/sources/chinese#cn01)）。HumanLayer 的观点相同：评审研究与计划的杠杆远高于评审代码（[VD20](/sources/vendors#vd20)）。

## 6. AI 代码评审：怎么用好

- **用仓库内文件定制**：REVIEW.md / CLAUDE.md 调整评审重点、减少吹毛求疵、忽略生成文件（[AN06](/sources/anthropic#an06)）。
- **规则从基础分支读取**，变更不能修改评判它的规则（[AN18](/sources/anthropic#an18)）。
- **多智能体投票降低误报**（[AN19](/sources/anthropic#an19)）。
- **按计划与准则检查**：Google Conductor 的 verify 步骤检查代码是否符合计划与准则（[BT04](/sources/bigtech#bt04)）。
- **不要神化**：Boris Cherny 的维护例程开了 388 个 PR，经 AI 评审 + 人工评审后合并 180 个（[X09](/sources/x-posts#x09)）——过半被拒，说明人工把关仍然必要。

## 7. 认知债与团队理解

Thoughtworks 把**代码库认知债**列为 Caution：系统实现与团队对「它如何、为何这样工作」的共同理解之间的差距在 AI 加速下扩大，而理解变弱又反过来削弱引导 AI、预判边界、避免架构漂移的能力（[TW30](/sources/thoughtworks#tw30)）。Kent Beck 警告：人人都会被推向「单人 AI 开发」，这是巨大的错误（[PR16](/sources/practitioners#pr16)）。Böckeler 等人指出，结对编程的价值包括知识传播与集体代码所有权，AI 助手不能替代这些社会功能（[TW13](/sources/thoughtworks#tw13)）；她也坚持「我依然在乎代码」——只要人仍对线上系统负责（[TW10](/sources/thoughtworks#tw10)）。

对策：

- 关键模块定期做「讲解式评审」：让智能体生成代码走读，人来提问（Simon Willison 的系列里有「线性走读」「交互式讲解」等章节，见 [PR07](/sources/practitioners#pr07)）。
- 保留人与人的结对/轮换，尤其是在架构边界与核心领域。
- 用 ADR 记录「为什么」（[TW35](/sources/thoughtworks#tw35)）。

## 与传统软件工程认知的对比

| 维度 | 传统认知 | 智能体时代 | 判断 |
| --- | --- | --- | --- |
| 代码评审 | 每个变更至少一人逐行评审 | 多层检查，按风险分配人的注意力（[AN19](/sources/anthropic#an19)、[TW26](/sources/thoughtworks#tw26)） | **修正**：评审从「必经关卡」变成「风险控制手段之一」 |
| 评审对象 | 代码 diff | 计划与方案的评审杠杆更高（[VD20](/sources/vendors#vd20)、[CN01](/sources/chinese#cn01)） | **前移** |
| 责任归属 | 作者 + 评审者共同负责 | 智能体不能负责；必须有一个人对合并代码负责（[X04](/sources/x-posts#x04)） | **延续并强化** |
| 小 PR 原则 | 小 PR 更易评审 | 更重要：AI 倾向大批量（[PR16](/sources/practitioners#pr16)、[PR12](/sources/practitioners#pr12)） | **延续并加强** |
| 结对编程 | 知识共享、质量 | 「与 AI 结对」不能替代人与人结对的社会功能（[TW13](/sources/thoughtworks#tw13)） | **延续**：两者互补 |
| 集体代码所有权 | 团队共同理解代码 | 认知债威胁这一点（[TW30](/sources/thoughtworks#tw30)） | **新风险** |

**选择理由**：逐行人工评审在传统团队里同时承担了「找 bug」「传播知识」「维护标准」「分担责任」四个职能。智能体时代，「找 bug」和「维护标准」可以大部分交给机械检查和 AI 评审；但「传播知识」和「承担责任」不能外包。因此新的评审体系应当：机械能做的全部自动化，把人的注意力集中在高风险变更、计划评审与团队理解上，而不是平均分配到每一行代码。

**证据强度**：「瓶颈转移到评审」是**共识**；风险分级是**雷达 Trial**；「人可以不评审」（OpenAI）是**厂商自报且有强前提**，属于**分歧**。
