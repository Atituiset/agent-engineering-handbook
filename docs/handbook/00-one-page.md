# 一页纸推荐：先读什么、先做什么、先别做什么

> 这一页只做一件事：从全书 14 章和原始资料里**挑出最值得先投入的少数几项**，每项写明推荐理由和证据强度。全书的结论与章节地图见 [导读](./)；skill 在全书框架里的定位见 [第 13 章 §0](./13-skills-catalog#book-view)；想要拿来就能跑的模板，见 [第 15 章 落地起步套件](./15-starter-kit)；评测怎么建、分数怎么读，见 [第 16 章 智能体评测](./16-agent-evals)；遇到「两种做法都有人推荐」时查 [决策指南](/compare/decision-guide)。

**证据标记**：**共识** = 多家独立来源一致；**分歧** = 有可信的相反证据；**待验证** = 单一来源；**厂商自报 / 团队自报** = 数字由发布方自己给出、未见独立复测。口径见 [导读 · 关于证据强度](./#关于证据强度)。

## 1. 一句话推荐 {#tldr}

先让仓库对智能体**可跑、可验证**，再把最重要的规则**变成检查**，最后才谈规则文件、skills 和并行。顺序反过来，规则写得再多也守不住：Anthropic 的官方文档明说，写进 CLAUDE.md 的规则遵不遵守由模型决定（[AN01](/sources/anthropic#an01)）。

```text
第 1 周   可跑：一条命令装好、跑测、起服务       → 11 §1、04 §9
第 2 周   可验证：先计划后编码，测试先红后绿       → 03、05
第 3 周   可强制：3–5 条架构规则写成 lint/测试/hook，CI 设必需检查 → 04、12
之后      可治理：沙箱、权限、回归评测、交付指标；再考虑 skills 与异步委派 → 09、05 §8、08、13、14
```

## 4. 按角色推荐 {#by-role}

### A. 刚开始用编码智能体的个人开发者 {#role-individual}

| 类别 | 推荐 | 理由 |
| --- | --- | --- |
| 先读 | [01 心智模型](./01-mental-model) → [02](./02-context-engineering) → [11 §8 会话卫生](./11-checklists#_8-会话卫生) | 先把它当「能力很强、没有长期记忆、急于交差的新同事」，就不会期待它自己守规矩；会话卫生是成本最低、见效最快的习惯 |
| 先做 | 用 [任务说明模板](./11-checklists#_3-任务说明模板) 写 Goal / Constraints / Done when；非小改动先让它出计划，你审完再在新会话执行 | 改一份 Markdown 计划比改一千行代码便宜（[03 §1](./03-spec-and-plan#_1-为什么计划先行)）；「先计划后编码」是几乎所有厂商与资深工程师的第一条建议（**共识**） |
| 先做 | 交差前自己跑过、亲眼看到它工作；测试先红后绿 | 智能体会删测试、在测试失败时宣告成功（[导读](./#你遇到的问题-大概率不是模型「不够聪明」)）；作者自证是 [11 §6](./11-checklists#_6-提交-pr-前自查-作者) 的第一条 |
| 先装 / 先用 | 先用默认配置；只装你技术栈对应的**厂商官方** skill，再自己写一个 `verify` skill | 「从朴素开始」（[07 §2](./07-harness-tools#_2-从朴素开始)）；官方 skill 补的是模型对新版 API 的知识滞后；verify 是最值得写的第一个 skill（[13 §0.2](./13-skills-catalog#starter-set)） |

### B. 要在团队里推广的 TL / 负责人 {#role-lead}

| 类别 | 推荐 | 理由 |
| --- | --- | --- |
| 先读 | [08 团队与流程](./08-team-process) → [06 评审](./06-review-collaboration) → [10 反模式](./10-anti-patterns) | 瓶颈会从「写」转到「审」再到 CI 与发布；不提前改评审方式，提效会被下游吃掉 |
| 先做 | 指定一名 harness 负责人（agents captain），维护共享的 AGENTS.md 与 skills；先在团队内对齐规范，再写成规则 | OpenAI 公开的推进清单第一条就包括「每个团队指定一名 agents captain」（[X04](/sources/x-posts#x04)，团队自报）；「先人人对齐，再人机对齐」（[08 §2](./08-team-process#_2-先人人对齐-再人机对齐)） |
| 先做 | 评审按风险分级；每段合并代码都有一个理解它的负责人 | 「有没有人读过代码」是不精确的代理指标（[06 §3](./06-review-collaboration#_3-风险分级)）；团队代码库「人要理解并为代码负责」是强共识（[P16](/compare/evidence#p16)） |
| 先做 | 用交付指标（回滚率、缺陷逃逸、评审等待、变更失败率）度量，不用 AI 代码占比 | Thoughtworks 把「以编码吞吐量衡量生产率」列为 Caution（[TW32](/sources/thoughtworks#tw32)）；快手 AI 代码占比上升后伴随技术债与线上故障（[CN06](/sources/chinese#cn06)，团队自报） |
| 先装 / 先用 | [13 §0.2](./13-skills-catalog#starter-set) 的团队组合：规范校验（agentskills）、评测（skill-up 或 waza），skill 目录纳入 CODEOWNERS | 团队 skill 是共识的固化，要像代码一样评审和回归 |

### C. 做平台、安全与治理的人 {#role-platform}

| 类别 | 推荐 | 理由 |
| --- | --- | --- |
| 先读 | [09 安全](./09-security) → [12 质量保障](./12-quality-cicd) → [14 异步智能体](./14-async-agents) | 智能体一旦在云端或 CI 里无人值守地跑，「人看着」的环节都要变成机制 |
| 先做 | 沙箱 + 网络白名单；专用、最小权限、短期凭据；三要素至少切断一条边 | 先限制爆炸半径，而不是让人逐条审批（[AN27](/sources/anthropic#an27)）；人工逐条确认并不可靠（[09 新证据](./09-security#new-evidence)，厂商自报） |
| 先做 | 主分支：必需检查 + 人工批准 + 禁止绕过；智能体账号与触发人都不能批准该 PR；CI 里的 AI 步骤不给 fork PR 密钥 | GitHub 给 Copilot 云端智能体内置的就是这套护栏（[QT15](/sources/quality/tools#qt15)），可直接作为基线（[11 §11](./11-checklists#_11-ci-与合并门禁-摘自第-12-章)） |
| 先做 | 规则文件、hooks、MCP 配置、skills、记忆文件、环境定义全部纳入 CODEOWNERS 与代码评审 | 它们都是供应链的一部分，MCP 工具描述和 `SKILL.md` 本身就能藏指令（[09 §3](./09-security#_3-供应链-新的攻击面)、[13 §6](./13-skills-catalog#security)） |
| 先装 / 先用 | 第三方 skill 先过扫描器（SkillSpector 等）再进 CI；可观测性按 OpenTelemetry 采集成本与工具调用 | 公开扫描数据显示注册表已遭投毒（厂商自报、**待验证**）；扫描只能降低风险，不能证明安全。遥测用于诊断与审计，不用于考核（[08 §8](./08-team-process#_8-遥测-看见智能体在做什么)） |

### D. 准备把任务交给云端或 CI 里的智能体 {#role-async}

| 类别 | 推荐 | 理由 |
| --- | --- | --- |
| 先读 | [14 §3 什么任务适合交出去](./14-async-agents#_3-什么任务适合交出去) → [§4 环境](./14-async-agents#_4-环境就是能力上限) | 适合委派的任务本身就是一份完整的 issue；智能体跑不了测试、起不了服务就无法闭环（[VD21](/sources/vendors#vd21)） |
| 先做 | 从批量迁移、补测试、依赖升级、lint 清理这类任务起步；CI 回合设上限，超过就交还给人 | 这些任务范围清楚、能自证、易回滚；Stripe 的无人值守智能体最多跑两轮 CI（[QB01](/sources/quality/bigtech#qb01)，厂商自报） |
| 先做 | 先算评审容量，再定并发数；先设预算 | 并发受评审容量与预算约束，而不是机器数量（[14 §7](./14-async-agents#_7-并发、成本与可恢复)） |

## 5. 立即可做的 8 件事 {#do-now}

按投入从小到大排列。每件都能在一个下午到一周内完成。

| # | 做什么 | 为什么 | 出处 |
| --- | --- | --- | --- |
| 1 | 测试、lint、类型检查、构建、启动都能**一条命令**跑通 | 智能体只有能跑检查才能自证；OpenAI 早期进展慢的原因就是环境欠规范（厂商自报） | [11 §1](./11-checklists#_1-新仓库接入智能体-第一周清单)、[04 §9](./04-architecture-constraints#_9-让代码库对智能体可读、可跑) |
| 2 | 写一份约 100 行以内的 AGENTS.md：命令、边界、非标准约定、坑点、文档索引 | 只写模型读不到、猜不到的东西，这是调和 §2 分歧证据的结论；常驻上下文是有限资源，越长越容易退化与冲突 | [02 §3](./02-context-engineering#_3-写法-一份好的-agents-md-包含什么)、[11 §2](./11-checklists#_2-agents-md-模板) |
| 3 | 把最重要的 3–5 条架构规则写成 lint 或结构测试，错误信息里写「怎么改」 | 能机械判定的规则交给确定性工具；报错信息就是提示词，失败会自动变成指导 | [04 §4](./04-architecture-constraints#_4-工具箱-把架构规则变成检查)、[11 §5](./11-checklists#_5-规则该放哪儿) |
| 4 | 保护检查本身：CI、lint 配置、架构测试设为受保护文件；加测试改动守卫 | 删测试、放宽断言、加 sleep 都是有记录的行为；变更不能修改评判它的规则 | [04 §5](./04-architecture-constraints#_5-保护检查本身)、[12 示例 B](./12-quality-cicd#example-b) |
| 5 | 开沙箱：工作区外只读、网络白名单、机密不进上下文 | 提示注入没有可靠的模型层解法；已发表的检测类防御在自适应攻击下多数失效（学术研究） | [09 §5](./09-security#_5-一个最小安全基线)、[11 §9](./11-checklists#_9-安全基线) |
| 6 | 主分支开必需检查与合并队列；AI 评审只作建议性初筛并记录解决率 | CI 是唯一不会被说服的评审者；AI 评审是第一道筛子，不是最后一道闸 | [12 §1](./12-quality-cicd#layers)、[12 示例 A](./12-quality-cicd#example-a)、[示例 D](./12-quality-cicd#example-d) |
| 7 | 挑 10–20 个代表任务做 harness 回归集，每个跑多次，改规则或换模型就重跑 | 没有评测只能「等投诉」；单次成功率 75%，连续 3 次都成功只有约 42%（[AN31](/sources/anthropic#an31)） | [05 §8](./05-verification#_8-评测-为团队的-harness-建回归)、[12 示例 C](./12-quality-cicd#example-c)；可运行的最小套件见 [16 §7](./16-agent-evals#starter) |
| 8 | 定下交付指标并每季度复盘 harness，删掉不再需要的规则 | 体感不可靠（METR）；每条规则都编码了一个会过期的假设，Anthropic 为新模型删掉了约 80% 的系统提示词（[XC-020](/sources/x/context#xc-020)，厂商自报） | [08 §3](./08-team-process#_3-度量-别被「ai-代码占比」骗了)、[11 §10](./11-checklists#_10-每季度-或每换一代模型-的-harness-复盘) |

**已做成模板的部分**：第 1、2、4、6 件事（一条命令跑通、短 AGENTS.md、保护检查本身、CI 必需检查）在 [第 15 章 落地起步套件](./15-starter-kit) 里已有 Python / TS / C++ / Java / Rust / C / Go 七个可直接 clone 的实现，并附实测的通过与拦截输出。

## 6. 先别做 / 常见误区 {#dont}

| 先别做 | 为什么 | 改为 |
| --- | --- | --- |
| 把「必须遵守」的规则只写进提示、AGENTS.md 或 skill | 遵守与否由模型决定（[AN01](/sources/anthropic#an01)）；skill 甚至可能根本不被调用（[VD11](/sources/vendors#vd11)，厂商自报） | hook、lint、CI 门禁（[反模式 1](./10-anti-patterns#_1-把规则写进提示-就以为它会被遵守)） |
| 规则越堆越多，或整包安装 awesome 列表、skill 大合集 | 指令有容量上限，冲突会让模型反复权衡；描述越多，误调用与上下文成本越高 | 失败驱动，一次加一个（[反模式 2](./10-anti-patterns#_2-指令膨胀)、[13 §0.3](./13-skills-catalog#dont)） |
| 按星标挑第三方 skill，或让它自动更新 | 星标只反映关注度；skill 注册表已出现投毒与仿冒（厂商自报） | 官方来源、固定 commit、看 diff 再更新（[13 §5](./13-skills-catalog#choose)） |
| 用公开基准分数选模型、调 harness | OpenAI 已停止报告 SWE-bench Verified，原因是测试缺陷与训练数据污染（[OA11](/sources/openai#oa11)，经第三方转述） | 用你自己仓库的回归集（[05 §8](./05-verification#_8-评测-为团队的-harness-建回归)） |
| 用「AI 代码占比」或「感觉更快了」证明成效 | 活动指标会落入古德哈特定律；体感与实测可能相反（[RS01](/sources/research#rs01)） | 交付指标 + 团队内小规模对照（[反模式 7](./10-anti-patterns#_7-用「ai-代码占比」衡量成功)、[16](./10-anti-patterns#_16-相信「感觉更快了」)） |
| 用同一个智能体既写又判，或允许变更修改评判它的检查 | 检查必须独立于被检查者，否则「通过」没有意义 | 生成者与评判者分离、受保护文件（[反模式 8](./10-anti-patterns#_8-让变更能修改评判它的检查)、[10](./10-anti-patterns#_10-用同一个智能体既写又判)） |
| 每个任务都套完整的规格驱动流程 | SDD 仍在早期，小任务套大流程只会制造文档 | 按任务规模选流程（[反模式 13](./10-anti-patterns#_13-对所有任务套用完整-sdd-流程)、[11 §4](./11-checklists#_4-选流程-任务规模速查)） |
| 把并行和多智能体当默认加速器 | 写操作并行会放大协调成本；并发受评审容量约束 | 读可以并行、写保持单线程（[反模式 12](./10-anti-patterns#_12-并行写手群)、[19](./10-anti-patterns#_19-把并行当成默认加速器)） |
| 让无人值守的智能体直接部署、迁移数据或改权限 | 异步智能体通常同时具备致命三要素，且没人盯着会话 | 留给人或单独的流水线（[14 §5](./14-async-agents#_5-身份、权限与审批)、[§7](./14-async-agents#_7-并发、成本与可恢复)） |

## 7. 读这一页时要记住的 {#caveats}

- **大部分建议来自厂商与个人的经验报告，对照研究很少。** 上表里标了「厂商自报 / 团队自报」的数字都没有独立复测，只能当方向参考。
- **「共识」的支持数是关键词自动归类的量级参考**，不是逐条人工复核的结果（[共识度/佐证 · 统计口径](/compare/evidence#method)）。
- **这一页会过期。** 模型换代后，第 5 节第 8 件事（复盘并删减规则）比任何一条具体建议都更持久。
