# 09 · 安全：给了它 shell 和网络之后

[[toc]]

> 本章只讨论防御性原则与工程控制，不涉及任何攻击细节。

## 要点

- **避免「致命三要素」同时存在**：私有数据 + 不可信内容 + 对外通信。更新的「二选规则」把「改变状态」也算进来：三项最多占两项。
- **提示注入目前没有可靠的模型层解法**，安全要靠架构：隔离、最小权限、数据流控制。已发表的检测类防御在自适应攻击下多数失效。
- **沙箱是默认，不是可选**：文件系统隔离 + 网络隔离。
- **规则文件、MCP 配置、skills、记忆文件都是供应链的一部分**，要像代码一样评审；MCP 工具描述本身也可能藏着指令。
- **依赖要校验**：AI 会推荐不存在的包，攻击者会抢注。
- **老的安全基本功依然最重要**：补丁、凭据管理、最小权限。

## 1. 第一原则：致命三要素

Simon Willison 提出（[SC01](/sources/security#sc01)）：当智能体同时具备**访问私有数据**、**暴露于不可信内容**、**对外通信能力**时，攻击者就能诱导它把数据发出去。我们仍无法 100% 可靠地防止这一点，「护栏」类产品不能保证安全。

> "The only way to stay safe there is to avoid that lethal trifecta combination entirely."

对编码智能体，三要素非常常见：读私有仓库（私有数据）+ 读 issue、网页、依赖代码（不可信内容）+ 能联网、能开 PR、能执行命令（对外通信）。Thoughtworks 雷达的「有毒流分析」就是专门识别这类数据流路径的技术（[TW25](/sources/thoughtworks#tw25)）。

**实践**：对每个智能体配置，画出这三项各自是否存在；**至少切断一条边**——例如处理不可信输入的智能体没有网络或没有写权限，或者有网络的智能体看不到机密数据。

**更新的框架：智能体的「二选规则」**。Meta 在 2025-10 提出 Agents Rule of Two（[SC10](/sources/security#sc10)）：在提示注入能被可靠检测之前，一个会话最多只应同时具备下面三项中的两项：

- **[A]** 处理不可信的输入；
- **[B]** 访问敏感系统或私有数据；
- **[C]** 改变状态或对外通信。

三项都需要时，智能体不应自主运行，至少要有人工审批或其他可靠的校验；也可以拆成新的会话（全新的上下文窗口）分步完成。它比致命三要素多考虑了「改变状态」：三要素只覆盖数据外泄，而改代码、删资源、发布同样可能由注入触发。Willison 认同这一补充，也指出一个漏洞：只有 [A] 和 [C] 的组合被标成「安全」，但即使没有私有数据，被注入后去改状态照样可能造成损害（[SC12](/sources/security#sc12)）。所以对编码智能体，[A]+[C] 也要放进沙箱或与生产隔离。

| 会话类型 | [A] 不可信输入 | [B] 私有数据 | [C] 改状态／外联 | 处理方式 |
| --- | --- | --- | --- | --- |
| 在本地私有仓库里写代码 | 去掉（只读本仓库与可信来源） | 有 | 有（写文件、跑命令） | 不让它读外部 issue、网页等不可信内容；必须联网查文档时按域名白名单，并把 [A] 当作仍然存在来对待 |
| 分诊公开 issue、读网页 | 有 | 去掉 | 有 | 沙箱内运行，不给机密 |
| CI 中自动修复，带写权限令牌 | 有（PR 内容、日志） | 有 | 有 | 三项全有：只开草稿 PR，合并由人审批（[第 14 章 §5](./14-async-agents#_5-身份、权限与审批)） |

## 2. 架构级防御

学术界提出了一组对提示注入具有可证明抵抗力的设计模式，核心是通过架构限制不可信输入能影响的动作范围，而不是依赖模型「自觉」（[SC02](/sources/security#sc02)）。OpenAI 的智能体构建指南也强调护栏要分层（[OA08](/sources/openai#oa08)）。工程上的落点：

- **沙箱**：Claude Code 用文件系统与网络两道边界，减少权限弹窗的同时降低注入危害（[AN27](/sources/anthropic#an27)）；Thoughtworks 雷达把智能体沙箱列为 Adopt（[TW24](/sources/thoughtworks#tw24)）。
- **限制爆炸半径**：把风险拆成「失败概率 × 失败后果」，重点限制后果（[AN28](/sources/anthropic#an28)）。
- **分类器式审批**：auto mode 用分类器拦截不符合用户意图的危险操作，代替让人疲劳的逐条确认（[AN26](/sources/anthropic#an26)）。
- **分层控制**：Anthropic 的大规模多智能体实验里，每个智能体在无网络沙箱中运行，执行前检查命令与编辑，另有离线监控（[AN34](/sources/anthropic#an34)）。
- **控制流与数据流分离**：CaMeL 让一个特权模型只根据可信的用户请求写出执行计划，另一个隔离的模型处理不可信数据但不能调用工具，数据还带着能流向哪里的标记；在 AgentDojo 基准上完成 77% 的任务，无防御时为 84%（[SC11](/sources/security#sc11)）。代价是一部分任务做不了，但安全性来自设计而非模型自觉。
- **云端隔离**：容器共享内核带来隔离风险，云端智能体需要更强的隔离边界（[VD10](/sources/vendors#vd10)）。异步与 CI 中智能体的身份、密钥与审批默认值见 [第 14 章 §5](./14-async-agents#_5-身份、权限与审批)。

**别指望单靠检测**。一项多机构合作的研究用自适应攻击（梯度、强化学习、随机搜索和人工红队）测试了 12 种已发表的提示注入防御，多数被攻破的成功率超过 90%，而这些防御原本报告的攻击成功率接近于零（[SC12](/sources/security#sc12)）。分类器和护栏可以降低风险，但不能替代上面的架构限制。

## 3. 供应链：新的攻击面

- **规则文件与 MCP**：被攻陷的 MCP 服务器、规则文件甚至依赖代码，都可能向智能体注入被操纵的指令（[TW12](/sources/thoughtworks#tw12)）。→ `AGENTS.md`、`.claude/`、`.cursor/rules`、skills、MCP 配置纳入代码评审与 CODEOWNERS；第三方 skills / hooks 引入前审查（[OS07](/sources/open-source#os07)）。恶意 skill 的公开数据与逐项审查清单见 [第 13 章 §6](./13-skills-catalog#security)。
- **包幻觉**：商业模型平均至少 5.2%、开源模型 21.7% 的推荐包不存在（[SC03](/sources/security#sc03)）；其中相当一部分幻觉稳定复现，可被抢注（slopsquatting，[SC04](/sources/security#sc04)）。→ 依赖白名单或私有镜像、新增依赖需人工确认、锁文件、依赖扫描。
- **OWASP LLM Top 10** 可作为威胁建模清单的起点（[SC05](/sources/security#sc05)）。

**接入 MCP 服务器前的审查清单**：

- **来源**：只用可信来源的服务器，锁定版本；本地服务器等同于在开发机上运行第三方代码，按规范要先征得用户同意，并且最好在沙箱里运行（[SC08](/sources/security#sc08)）。
- **工具描述也要审**：工具的描述和参数说明会原样进入模型上下文，可能藏着用户看不到的指令（tool poisoning）；服务器还可能在获得批准后悄悄修改描述。对已批准的工具定义做哈希锁定，变更时重新审批（[SC09](/sources/security#sc09)）。
- **授权**：远程服务器走 OAuth 2.1，令牌只能用于签发给它的那个服务器；规范明确禁止把客户端拿到的令牌原样透传给下游 API（[SC08](/sources/security#sc08)）。
- **最小范围**：只申请当前任务需要的权限范围，不要一次要全；注意混淆代理（confused deputy）和服务端请求伪造（SSRF）这两类规范专门列出的风险（[SC08](/sources/security#sc08)）。
- **数量**：每多一个服务器，就多一份攻击面，也多一份上下文成本（[第 07 章 §5](./07-harness-tools#_5-工具设计-接口比示例重要)）。

## 4. 基本功依然最重要

Cognition 的安全指南提醒：多年来已知的最佳实践依然有效——攻击者利用未打补丁的服务器或被盗凭据并不需要高级 AI；AI 让攻击更快更便宜，但不妨碍你关闭基础攻击路径（[SC06](/sources/security#sc06)）。

对使用智能体的团队：

- 智能体使用**专用、最小权限、短期**的凭据，绝不复用个人长期令牌；
- 机密不进仓库、不进上下文；
- 生产环境的写操作需要人工批准；
- 智能体的操作有审计日志（OpenAI 也建议追踪产生代码的智能体轨迹，[X04](/sources/x-posts#x04)）；
- 安全评审作为可阻断的检查层（[AN19](/sources/anthropic#an19)）；
- 安全敏感代码按高风险等级评审（第 06 章）。

## 5. 一个最小安全基线

| 控制 | 默认值 |
| --- | --- |
| 文件系统 | 仅限当前工作区可写 |
| 网络 | 默认关闭，按域名白名单开放 |
| 命令 | 危险命令 deny 规则（强制推送、删除、发布、`--no-verify` 等） |
| 凭据 | 专用、最小权限、短期；不在上下文中出现 |
| 依赖 | 新增依赖需人工确认 |
| 配置 | 规则文件 / hooks / MCP 配置 / 记忆文件走代码评审；MCP 工具定义锁定版本或哈希 |
| 不可信输入 | 按「二选规则」：处理不可信内容的会话，不同时拥有私有数据与改状态／外联能力；三项都需要时必须人工审批 |
| 审计 | 会话、工具调用和审批决定可追溯（[第 08 章 §8](./08-team-process#_8-遥测-看见智能体在做什么)） |

## 2026-11 新证据：真实事故与人工确认的失效 {#new-evidence}

P15「最小权限与沙箱」有 179 位独立支持，几乎没有人反对它本身，争论在于「怎么做」。

- **事故复盘**：PocketOS 事件中，智能体处理测试环境报错时，在代码库里找到一个与任务无关的云服务 Token，9 秒内删除了生产数据卷及卷级备份（二手复盘，[CN50](/sources/chinese#cn50)）。教训与本章一致：凭据不进代码库，高危操作需要独立凭证与二次确认。HN 上还有 Gemini CLI 删除用户文件（[HN24](/sources/hackernews#hn24)）、Codex 在没有 sudo 时借 docker 组权限绕过限制（[HN12](/sources/hackernews#hn12)）等讨论。
- **数据外泄面**：接入数据库 MCP 的智能体可能因数据中的提示注入而泄露数据（[HN05](/sources/hackernews#hn05)）。dex 记录了企业 CISO 在「给智能体接工具」与「防外泄」之间的权衡（[XS-009](/sources/x/security#xs-009)）。
- **人工确认不可靠**：Anthropic 的实验里人工只发现 13.6% 的危险命令（厂商自报，[XS-006](/sources/x/security#xs-006)）。厂商因此推荐用 auto mode 加分类器替代逐条批准（[XA-012](/sources/x/parallel#xa-012)），并称多层防护让间接提示注入在未见攻击上接近 0（厂商自报，[XS-005](/sources/x/security#xs-005)）。这**加强**了本章「审批疲劳 → 沙箱 + 分类器」的判断，但这个数字未见独立复测；自适应攻击研究显示，原本报告接近零的防御多数会被攻破（[SC12](/sources/security#sc12)），所以分类器只能是架构限制之外的一层。
- **数据边界与沙箱基建**：用商业编码工具处理私有代码前，要单独评估遥测与数据边界——独立研究者发现 Trae 在关闭遥测后仍上报多类数据（[BD19](/sources/security#bd19)）。需要更强的数据边界时，可以考虑私有化部署或开放权重模型，能力与成本的取舍见 [第 07 章 §9](./07-harness-tools#_9-成本与模型选择)。腾讯开源了仓库级的 AI 生成代码安全评测 A.S.E（[TX22](/sources/security#tx22)）；沙箱隔离方面，阿里 OpenSandbox（团队自报，[AL07](/sources/chinese#al07)）与腾讯 CubeSandbox（[TX19](/sources/open-source#tx19)）都已开源。

## 与传统软件工程认知的对比

| 维度 | 传统认知 | 智能体时代 | 判断 | 佐证（支持／异议） |
| --- | --- | --- | --- | --- |
| 最小权限 | 经典原则，但开发机上常被忽视 | 智能体必须最小权限（[TW24](/sources/thoughtworks#tw24)） | **延续并强化** | [P15 · 179／10](/compare/evidence#p15) |
| 代码与数据分离 | SQL 注入的教训：不要把数据当代码执行 | 提示注入是同一问题的新形态，且没有「参数化查询」式的根治方案（[SC01](/sources/security#sc01)）；CaMeL 等设计在架构上分离控制流与数据流（[SC11](/sources/security#sc11)） | **延续**，但更难 | [P15 · 179／10](/compare/evidence#p15) |
| 供应链安全 | 依赖扫描、SBOM | 新增包幻觉、规则文件、MCP 等攻击面（[SC03](/sources/security#sc03)、[TW12](/sources/thoughtworks#tw12)） | **扩展** | [P15 · 179／10](/compare/evidence#p15) |
| 人工审批 | 每个危险操作都要人确认 | 审批疲劳让确认失效（93% 被批准），改用沙箱 + 分类器（[AN26](/sources/anthropic#an26)） | **修正** | [P15 · 179／10](/compare/evidence#p15) |
| 安全基本功 | 补丁、凭据、最小权限 | 依然是第一优先级（[SC06](/sources/security#sc06)） | **延续** | [P15 · 179／10](/compare/evidence#p15) |

> 「佐证」列：原则编号 · 独立支持作者数／异议数（疑似 + 人工确认），关键词自动归类，口径见 [共识度/佐证](/compare/evidence)。

**选择理由**：提示注入本质上是「代码与数据混在同一通道」的老问题，而 LLM 天然无法区分两者。在没有根治方案的情况下，唯一可靠的做法是经典的纵深防御：限制每个组件能做什么（最小权限）、能看到什么（数据隔离）、能和谁通信（网络隔离），并假设模型层的防护随时会失效。

**证据强度**：致命三要素与沙箱是**共识**；二选规则是**单一厂商框架**，已有知名实践者的批评；包幻觉数据、CaMeL 与自适应攻击来自**学术研究**；MCP 授权要求来自**协议规范**；厂商的具体防御效果是**厂商自报**，均未见独立复测；PocketOS 事件（[CN50](/sources/chinese#cn50)）是二手复盘，只作示例。
