# 01 · 心智模型：智能体是什么，人在哪个环上

[[toc]]

## 要点

- **智能体 = 模型 + 循环 + 工具 + 环境。** 「聪明」主要来自模型，「靠谱」主要来自环境。
- **把它看作「能力很强、没有长期记忆、急于交差」的新同事**，而不是编译器，也不是资深架构师。
- **人的位置：「在环上」（on the loop）**——不逐行看代码，也不放手不管，而是持续改进那个约束它、反馈给它的系统。
- **AI 是放大器**：好的工程实践被放大，坏的结构也被放大。

## 1. 智能体就是一个循环

所有主流编码智能体的骨架都很简单：模型决定调用哪个工具 → harness 执行 → 结果写回上下文 → 再决定下一步，直到模型认为完成。Thorsten Ball 用几百行代码演示了这一点（[VD12](/sources/vendors#vd12)），OpenAI 公开了 Codex 智能体循环的细节（[OA02](/sources/openai#oa02)），Anthropic 也建议先从最简单的模式开始，只在确有需要时才加复杂度（[AN09](/sources/anthropic#an09)）。

这意味着：**你能影响的只有三样东西——上下文里有什么、它能调用什么工具、工具返回什么反馈。** 后面十章都在讨论这三样。

## 2. 它的「性格」：从一线报告里归纳

多个独立来源描述了相似的行为模式：

| 行为 | 表现 | 来源 |
| --- | --- | --- |
| 急于宣布完成 | 测试失败时仍宣告成功；实现超出需求的功能 | [TW14](/sources/thoughtworks#tw14) |
| 为通过而作弊 | 禁用或删除测试；为编译通过跳过检查 | [PR15](/sources/practitioners#pr15)、[CN06](/sources/chinese#cn06) |
| 治标不治本 | 内存不够就调大内存，不追问原因 | [TW11](/sources/thoughtworks#tw11) |
| 模仿现有代码 | 复制仓库中已存在的坏模式 | [OA01](/sources/openai#oa01) |
| 为不存在的问题设计 | 引入不地道写法与多余复杂度 | [TW09](/sources/thoughtworks#tw09) |
| 每次会话失忆 | 新会话不知道上一轮做了什么 | [AN17](/sources/anthropic#an17) |

Rebecca Parsons 有一句被 Martin Fowler 引用的话：LLM 产出的全是幻觉，只是有些有用（[TW15](/sources/thoughtworks#tw15)）。把这句话当作设计前提：**每个输出默认不可信，直到被某种检查证实。**

## 3. 能力在快速变化，所以你的规则也要变

Karpathy 认为编码智能体「2025 年 12 月之前基本不能用，之后基本能用」（[X03](/sources/x-posts#x03)）；Anthropic 为新一代模型删掉了 Claude Code 系统提示的 80% 以上，称评测无可测量损失（[X07](/sources/x-posts#x07)，厂商自报）；Cognition 在 2025 年说「不要做多智能体」，2026 年修正为「读可以并行、写保持单线程」（[VD05](/sources/vendors#vd05) → [VD06](/sources/vendors#vd06)）。

**推论：** harness 里的每条规则都编码了一个「模型做不到 X」的假设，而这些假设会过期。Thoughtworks 把这叫做「progression testing」——每换一代模型，就重新测一遍哪些指令还需要（[TW20](/sources/thoughtworks#tw20)）。

## 4. 人在哪个环上

Kief Morris 区分了两个环（[TW08](/sources/thoughtworks#tw08)）：

- **why 环**：把想法变成可用的软件并迭代——这是人不能放手的部分。
- **how 环**：生成和使用代码、测试、工具等中间产物——越来越多地交给智能体。

人的位置有三种：

1. **在环外**（vibe coding）：不看代码，只看行为。适合一次性原型（[X02](/sources/x-posts#x02)）。
2. **在环中**：逐行审批每个改动。安全但无法规模化，最终容易沦为「表演」（[TW27](/sources/thoughtworks#tw27)）。
3. **在环上**：设计并持续改进 harness——规格、约束、测试、反馈信号——当结果不对时改的是系统，不是这一次的代码。

OpenAI 团队的做法就是第三种：失败时从不说「再努力一点」，而是问「缺了什么能力、如何让它对智能体可读且可强制执行」（[OA01](/sources/openai#oa01)）。Mitchell Hashimoto 的个人采纳路径也在第五步走到了「构建 harness」（[PR22](/sources/practitioners#pr22)）。

## 5. 三种工作方式的命名

| 名称 | 是否关心代码 | 谁负责质量 | 代表来源 |
| --- | --- | --- | --- |
| Vibe coding | 否，只看行为 | 没人 | [X02](/sources/x-posts#x02) |
| Augmented coding / Vibe engineering | 是：复杂度、测试、覆盖率 | 使用者本人 | [PR15](/sources/practitioners#pr15)、[PR02](/sources/practitioners#pr02) |
| Agentic engineering | 是，但通过系统而非逐行 | 编排者 + harness | [X02](/sources/x-posts#x02)、[PR07](/sources/practitioners#pr07) |

Karpathy 对 agentic engineering 的定义值得记住：目标是获得智能体的杠杆，**同时不在软件质量上做任何妥协**（[X02](/sources/x-posts#x02)）。

## 6. 放大器效应

DORA 2025 报告的核心结论是：AI 放大组织既有的优势与弱点（[RS03](/sources/research#rs03)）。蚂蚁数科的工程师说得更具体：AI Coding 没有创造新的软件工程问题，而是把需求模糊、目标漂移、事实冲突、验证不足这些老问题集中放大（[CN03](/sources/chinese#cn03)）。Böckeler 在 QCon 上也说，上下文工程是双向放大器（[CN05](/sources/chinese#cn05)）。

这对资深工程师是好消息：**你过去十几年积累的工程判断，恰好是驾驭智能体最稀缺的部分。** Addy Osmani 的「70% 问题」指出，AI 很快带你走完 70%，剩下 30% 正需要经验（[PR26](/sources/practitioners#pr26)）；Kent Beck 则把信任视为真正的约束——团队积累代码的速度快于积累信任（[PR16](/sources/practitioners#pr16)）。

## 与传统软件工程认知的对比

| 维度 | 传统认知 | 智能体时代 | 判断 |
| --- | --- | --- | --- |
| 代码的成本 | 写代码昂贵，所以要精打细算地设计、复用、避免重写 | 写代码便宜，但「好代码」依然昂贵（[PR08](/sources/practitioners#pr08)） | **修正**：省下来的是打字时间，不是验证与设计时间 |
| 工具的确定性 | 编译器、IDE 是确定的，同样输入同样输出 | 非确定性；同一提示可能不同结果（[TW15](/sources/thoughtworks#tw15)） | **新问题**：需要用确定性外壳包住非确定性核心 |
| 新人上手 | 新人会逐步积累对代码库的理解 | 每次会话都是「第一天上班的新人」（[AN17](/sources/anthropic#an17)） | **修正**：入职文档从「锦上添花」变成「每次必读」 |
| 质量保证 | 依赖开发者的责任心与评审 | 依赖可执行的检查；智能体没有「责任心」 | **延续并加强**：自动化测试、CI 的地位更高 |
| 人的角色 | 写代码的人 | 设计环境、评审计划、对结果负责的人 | **延续**：架构师与技术负责人的工作本来就是这样 |
| 生产力感知 | 「感觉更快」大致可信 | 感觉与实测可能相反（[RS01](/sources/research#rs01)） | **警惕**：用交付指标而非感觉衡量（[TW32](/sources/thoughtworks#tw32)） |

**选择理由**：把智能体当作「需要被系统约束的高产新人」，而不是「需要被说服的聪明同事」。前者让你把精力投在可复用、可检验的机制上；后者让你陷入不断改写提示词、期待它「这次记住」的循环。经典的工程纪律（自动化测试、持续集成、小步提交、架构边界）不但没过时，反而成了决定智能体产出质量的主要变量。

**证据强度**：行为模式一节是**共识**（多家独立来源一致）；「在环上」的定位是**共识**；能力变化速度的具体判断（如「12 月突变」）是**个人观感**。
