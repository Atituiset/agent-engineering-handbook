# 14 · 异步与后台智能体：把任务交出去之后

[[toc]]

## 要点

- **人不在现场，前面各章里「人看着」的环节都要变成机制。** 验证、门禁、权限和交接都不能再靠有人盯着会话。
- **适合交出去的任务，本身就是一份完整的 issue**：范围清楚，有可执行的完成标准，能在环境里自证，失败了也容易回滚。需要中途反复澄清的任务，先做计划（第 03 章），不要直接委派。
- **环境决定能力上限。** 智能体跑不了测试、起不了服务，就无法闭环。环境定义要入库、走评审、可复用。
- **智能体有自己的身份，而且不能批准自己。** 触发任务的人也不能批准它的 PR；CI 里的 AI 步骤只拿最小权限，不给不可信输入配密钥。
- **交回给人的必须是证据，不是「我做完了」**：通过的检查、截图或日志、未完成项。CI 回合要设上限，超过就交还给人。
- **并发受评审容量和预算约束，而不是受机器数量约束。** 长任务要能从中断处继续，有副作用的操作要能安全重放。

> 本章把散落在第 05、07、08、09、12 章的相关做法集中起来，讲「委派」这种工作方式本身。CI 门禁的配置细节见 [第 12 章](./12-quality-cicd)，安全原则见 [第 09 章](./09-security)。

## 1. 什么变了：从「结对」到「委派」

交互式使用时，人和智能体在同一个会话里，随时可以纠偏。异步使用时，人只在开头写任务、在结尾看结果。Cognition 称 Devin 由异步触发的会话首次超过了交互式会话，所以开发者回来时必须看到「已验证、可合并」的结果（[VD09](/sources/vendors#vd09)，厂商自报）。

主要厂商都把这种形态做成了正式产品，文档也写得很具体：

- **OpenAI Codex Cloud**：每个任务有独立工作区，电脑休眠时也能继续；环境可以发布后复用（[OA10](/sources/openai#oa10)）。
- **Cursor Cloud Agents**（原 Background Agents）：在隔离虚拟机里运行，可从 Slack、GitHub 评论、Linear 或 API 发起（[VD21](/sources/vendors#vd21)）。
- **GitHub Copilot**：把一次委派拆成客户端、会话、环境三部分，环境可以是云端沙箱或 Actions runner（[BT20](/sources/bigtech#bt20)）。

自建平台的大厂案例（均为团队自报）：Stripe 的 Minions 从一条 Slack 消息开始、以一个通过 CI 的 PR 结束，中间没有人工交互，每周有上千个这样的 PR 合并，全部经过人工评审（[QB01](/sources/quality/bigtech#qb01)）。Spotify 的后台智能体合并了 1,500 多个 PR，关键设计是「周边基础设施不变」（[QB04](/sources/quality/bigtech#qb04)）。腾讯轻量云团队的 LoopForge 走过了云端工作区、共享会话、硬门禁 SOP、无人值守自动化这几步（[CN20](/sources/chinese#cn20)）。

## 2. 四种形态

| 形态 | 怎么触发 | 在哪里跑 | 产出 | 最需要注意 | 例子 |
| --- | --- | --- | --- | --- | --- |
| 云端任务 | 人从聊天、IDE 或手机交出去 | 厂商托管的虚拟机或容器 | 分支、PR、产物 | 环境是否完整；密钥与网络范围 | [OA10](/sources/openai#oa10)、[VD21](/sources/vendors#vd21) |
| 事件触发 | 指派 issue、在 PR 或 issue 下评论、Slack 消息 | 同上，或 Actions runner | PR 或评论 | 触发内容是**不可信输入**；谁有权触发 | [BT20](/sources/bigtech#bt20)、[QT05](/sources/quality/tools#qt05) |
| CI 工作流中的步骤 | PR 事件、定时任务 | CI runner | 评审意见、修复提交 | 工作流权限、fork PR 与密钥 | [QT05](/sources/quality/tools#qt05)、[QT12](/sources/quality/tools#qt12) |
| 自建平台 | 内部系统、批量任务 | 自有 devbox 或沙箱 | 大批量 PR | 编排、验证服务、评审容量 | [QB01](/sources/quality/bigtech#qb01)、[QB05](/sources/quality/bigtech#qb05) |

## 3. 什么任务适合交出去

GitHub 的建议是：把分配给智能体的 issue 当作提示来写，写清问题、验收标准与涉及的文件。范围清晰的任务适合交给智能体；复杂、跨仓库、需要深厚领域知识，或涉及生产关键、安全敏感逻辑的任务，更适合人自己做（[BT14](/sources/bigtech#bt14)）。OpenAI 内部的经验是任务粒度大约为「人类一小时、几百行」，提示要像写 GitHub issue 一样具体（[OA05](/sources/openai#oa05)，厂商自报）。GitHub 博客的 WRAP 法则也要求拆成原子任务（[BT17](/sources/bigtech#bt17)）。

委派前逐条确认：

- [ ] 有可执行的完成标准（测试、命令、页面上能看到的结果），写在任务里（[第 11 章 §3](./11-checklists#_3-任务说明模板)）
- [ ] 智能体能在它的环境里自己验证，不需要人帮它看
- [ ] 改动范围小，PR 可以单独评审、单独回滚
- [ ] 不需要中途做产品或架构决策；如果需要，先在交互式会话里做完计划（[第 03 章](./03-spec-and-plan)）
- [ ] 不涉及生产数据、密钥轮换、权限变更这类高风险操作

**最适合的任务**：批量迁移、补测试、依赖升级、lint 告警清理、文档修复，以及有明确复现步骤的 bug。Spotify 的后台智能体主要就用于大规模迁移与维护（[QB04](/sources/quality/bigtech#qb04)）。Mitchell Hashimoto 所说的「有把握的灌篮任务」也属于这一类（[PR22](/sources/practitioners#pr22)）。

## 4. 环境就是能力上限

Cursor 的文档把这一点写得很直接：智能体能写代码却跑不了测试、查不了服务、调不了 API，就无法闭环；配置开发环境是提升云端智能体效果最重要的一步（[VD21](/sources/vendors#vd21)）。

> "Agents are only as capable as the environments they run in."

做法：

- **环境定义入库**：安装脚本、Dockerfile 或厂商的环境配置文件提交进仓库，走代码评审；改了环境就像改了 CI 一样要有人看。Codex 和 Cursor 都支持可复用的环境定义（[OA10](/sources/openai#oa10)、[VD21](/sources/vendors#vd21)）。OpenAI 建议持续改进启动脚本和环境变量，以减少出错（[OA05](/sources/openai#oa05)）。
- **一条命令完成安装、启动、测试**：这正是 [第 11 章 §1](./11-checklists#_1-新仓库接入智能体-第一周清单) 的第一条，在异步场景里没有它，智能体就只能「猜」。
- **网络默认只开包管理器**，其余按域名加白名单；密钥只对需要的域名生效（[OA10](/sources/openai#oa10)）。
- **云端与本地的 harness 保持一致**：仓库里的 hooks 在 Cursor 云端照常执行，用户目录下的个人 hooks 则不会生效（[VD21](/sources/vendors#vd21)）。必须执行的检查要放在仓库级配置里。
- **验证运行时与智能体运行时分离**：Spotify 起初在智能体的虚拟机里重造 CI，后来改由验证服务调用真实 CI，再把失败摘要回给智能体（[QB05](/sources/quality/bigtech#qb05)）。

## 5. 身份、权限与审批

异步智能体通常同时具备致命三要素：能读私有仓库，会读到 issue、评论、网页等不可信内容，还能推分支、开 PR、联网（[第 09 章 §1](./09-security#_1-第一原则-致命三要素)）。因此权限要按「一个刚入职、会被社会工程攻击的同事」来配。

GitHub 给 Copilot 云端智能体内置的护栏可以作为基线：智能体不能把自己的 PR 标为待评审，不能批准或合并；触发任务的人也不能批准该 PR；默认要等有写权限的用户批准后，PR 上的 Actions 工作流才会运行（[QT15](/sources/quality/tools#qt15)）。CI 里的 AI 步骤同理：Anthropic 的安全评审 Action 明确说没有针对提示注入加固，只应评审可信 PR（[QT06](/sources/quality/tools#qt06)）；fork 来的 PR 拿不到密钥（[QT05](/sources/quality/tools#qt05)）；codex-action 可以配置为只读、不联网，并建议使用一次性 runner（[QT12](/sources/quality/tools#qt12)）。

| 控制 | 默认值 |
| --- | --- |
| 身份 | 专用机器人账号或 App，不复用个人令牌 |
| 写权限 | 只能推自己的分支、开 PR；不能直接推主分支 |
| 批准 | 智能体账号与触发人都不在可批准者之列（[第 12 章示例](./12-quality-cicd#examples)） |
| 触发 | 只有仓库成员能触发；外部 issue 要先由成员加标签 |
| 密钥 | 按任务、按域名最小化注入；fork PR 和不可信触发不带密钥 |
| 网络 | 默认只开包管理器，其余白名单 |
| 环境与 harness 配置 | 环境定义、AGENTS.md、hooks、工作流文件纳入 CODEOWNERS |
| 审计 | 保留会话记录、工具调用与产生的提交，可追溯到触发人 |

## 6. 交回给人：证据、回合上限与升级

```text
任务（issue / 评论 / 定时）
  → 隔离环境：实现 + 自测
  → CI 必需检查
      ├─ 通过 → 人工评审 ──┬─ 批准 → 合并队列
      │                    └─ 要求修改 → 回到实现
      ├─ 失败，未到回合上限 → 回到实现
      └─ 失败，已到回合上限 → 交回给人
```

- **交回的是证据**：Cognition 让开发者回来时看到「已验证、可合并」的结果，并用带标注的截图方便复核（[VD09](/sources/vendors#vd09)）；Cursor 的云端智能体在 PR 里附截图、视频和日志（[VD21](/sources/vendors#vd21)）。PR 描述至少要写清：任务来源、做了什么、怎么验证的、哪些没做。
- **回合要设上限**：Stripe 的无人值守智能体最多跑两轮 CI，然后交回工程师（[QB01](/sources/quality/bigtech#qb01)）；LoopForge 的每个 SOP 节点都有重试上限，防止死循环（[CN20](/sources/chinese#cn20)）。没有上限，智能体会「试」出一个碰巧通过的版本（[第 12 章 §1](./12-quality-cicd#layers)）。
- **评审按风险分级**：异步产出的 PR 数量会迅速超过评审容量。低风险改动看自动检查和范围，高风险改动仍需逐行评审（[第 06 章 §3](./06-review-collaboration#_3-风险分级)）。

## 7. 并发、成本与可恢复

- **并发度由下游决定**：如果审批者还在手动审 PR，后台智能体再多也会被卡住（[CN33](/sources/chinese#cn33)）。数百个云端智能体需要编排、治理，还要接入各种系统（[VD10](/sources/vendors#vd10)）。先算评审容量，再定并发数；不要把并行当默认加速器（[第 10 章 · 反模式 19](./10-anti-patterns#_19-把并行当成默认加速器)）。
- **预算要先设**：Cursor 首次使用云端智能体时要求设置花费上限，按所选模型计费，选更大的上下文窗口会增加 token 用量（[VD21](/sources/vendors#vd21)）。团队层面要给每类任务设预算，并跟踪「每个合并 PR 的成本」。
- **能从中断处继续**：虚拟机回收、配额耗尽、超时都会打断长任务。可以用进度文件与 git 交接（[AN17](/sources/anthropic#an17)），也可以用框架的检查点机制，例如 LangGraph 的持久化层就是为「中断后恢复、从失败中恢复」设计的（[VD22](/sources/vendors#vd22)）。腾讯云 ADP 把循环、记忆、沙箱与工具解耦，让容器崩溃后可以恢复（[TX06](/sources/chinese#tx06)）。
- **副作用要能安全重放**：如果任务里有发评论、改工单、调外部 API 这类操作，就要做到重复执行不出错（幂等），或者把这类操作留给人或单独的流水线。部署、数据迁移、权限变更不应交给无人值守的智能体直接执行（[第 09 章 §4](./09-security#_4-基本功依然最重要)）。

## 2026-11 新证据 {#new-evidence}

- **产品形态在快速收敛**：Cursor 把 Background Agents 更名为 Cloud Agents（[VD21](/sources/vendors#vd21)）；GitHub 在 2026-10-28 推出新的「Copilot in the cloud」体验，会话可在网页、IDE、手机、CLI 之间接续（[BT20](/sources/bigtech#bt20)）。三家文档都把**环境配置**和**网络与密钥控制**放在核心位置，这与本章的判断一致。
- **评审与修复开始闭环**：Cursor 的 Bugbot Autofix 发现问题后派云端智能体在独立虚拟机里修复，称超过 35% 的修改被合并进原 PR（厂商自报，[QT23](/sources/quality/tools#qt23)）。修复仍以 PR 形式交给人，这符合「智能体不能批准自己」的原则。
- **云端沙箱成为前提**：Guillermo Rauch 认为新一代模型能承担的并行工作远超一台电脑的承载能力，因此需要云端沙箱（[XA-021](/sources/x/parallel#xa-021)；厂商自报，Vercel 本身提供沙箱产品）。
- **大规模案例都把人留在合并环节**：Stripe、Spotify 的大批量 PR 全部经过人工评审，Spotify 还明确要求选仓库、开 PR、评审、合并的流程与人工改动完全相同（[QB01](/sources/quality/bigtech#qb01)、[QB04](/sources/quality/bigtech#qb04)，团队自报）。目前还没有看到让智能体自行合并生产代码的公开大规模实践。

## 与传统软件工程认知的对比

| 维度 | 传统认知 | 智能体时代 | 判断 | 佐证（支持／异议） |
| --- | --- | --- | --- | --- |
| 派任务 | 给同事派 issue，对方会追问、会补全背景 | 智能体在无人时不会追问，issue 本身必须是完整规格（[BT14](/sources/bigtech#bt14)、[OA05](/sources/openai#oa05)） | **修正** | [P01 · 260／14](/compare/evidence#p01) |
| 开发环境 | 每人自己配本地环境，靠 README | 环境是入库、可复用的团队资产，决定智能体的能力上限（[VD21](/sources/vendors#vd21)） | **修正** | [P06 · 298／18](/compare/evidence#p06) |
| CI 机器人 | 只跑固定脚本，权限给大一点无妨 | CI 里的 AI 步骤会读不可信输入并自主行动，要按最小权限管理（[QT06](/sources/quality/tools#qt06)） | **修正** | [P15 · 179／10](/compare/evidence#p15) |
| 职责分离 | 作者不能批准自己的 PR | 扩展到智能体本身和触发它的人（[QT15](/sources/quality/tools#qt15)） | **延续并扩展** | [Q03 · 89／5](./12-quality-cicd#q03) |
| 异步协作 | 跨时区协作靠清晰的交接文档 | 智能体之间、智能体与人之间同样靠进度文件和产物交接（[AN17](/sources/anthropic#an17)） | **延续** | [P18 · 171／3](/compare/evidence#p18) |
| 并发上限 | 由机器和人手数量决定 | 由评审容量和预算决定（[CN33](/sources/chinese#cn33)） | **修正** | [P11 · 209／17](/compare/evidence#p11) |

> 「佐证」列：原则编号 · 独立支持作者数／异议数（疑似 + 人工确认），关键词自动归类，口径见 [共识度/佐证](/compare/evidence)；Q 编号的口径见 [第 12 章 · 共识度](./12-quality-cicd#consensus)。

**选择理由**：委派是一种很老的管理问题：任务写清楚、给对方需要的工具、设好权限边界、要求对方带着证据交付、对结果负最终责任。智能体时代没有改变这些原则，只是把它们的代价放大了：对方不会追问、会被不可信内容操纵、可以同时开几百个分身。所以本章的大部分建议都是经典的分派与职责分离纪律，只是全部写成了机制。

**证据强度**：「人留在合并环节、智能体不能自批」是**共识**，厂商护栏与大厂案例一致；任务粒度与适用范围是**厂商经验**；大厂的 PR 数量与 Autofix 合并率都是**团队或厂商自报**；异步智能体对交付指标的净效果，目前**没有独立研究**。
