### QT01 · Anthropic：智能体 Evals 解惑——任务、试验、评分器与回归集 {#qt01}
**作者/机构**：Anthropic｜**日期**：2026-01-09｜[原文](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

系统讲解如何为智能体做自动化评测：区分任务、试验（trial，多次运行以对冲非确定性）、评分器、转录与最终状态（outcome）；尽量用确定性检查判断环境最终状态，模型评分器用于开放性质量，并以人工复核校准。区分“能力评测”（攻难题）与“回归评测”（防退化）；建议从真实失败中整理 20–50 个任务起步。文中指出：没有 evals 的团队在新模型发布时要花数周测试，有 evals 的团队几天就能升级。

> “Evals make problems and behavioral changes visible before they affect users, and their value compounds over the lifecycle of an agent.”

**证据类型**：厂商自报｜**对应原则**：[Q08](/handbook/12-quality-cicd#q08) [Q12](/handbook/12-quality-cicd#q12)

### QT02 · Anthropic：长时运行智能体的 harness——禁止删改测试，强制端到端验证 {#qt02}
**作者/机构**：Anthropic｜**日期**：2025-11-26｜[原文](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

构建长时运行的编码智能体时，Anthropic 让初始化智能体生成功能清单 JSON，编码智能体只能修改其中 `passes` 字段，并用强硬措辞禁止删除或修改测试。观察到的主要失败模式之一是：不做充分测试就把功能标记为完成；明确要求用浏览器自动化“像真实用户一样”端到端测试后，表现显著改善。还建议写 `init.sh` 启动开发服务器，并在实现新功能前先跑一遍基本端到端测试。（此链接 v2 已收录，本专题从质量保障角度重读。）

> “It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality.”

**证据类型**：厂商自报｜**对应原则**：[Q04](/handbook/12-quality-cicd#q04) [Q02](/handbook/12-quality-cicd#q02) [Q05](/handbook/12-quality-cicd#q05)

### QT03 · Claude Code 最佳实践：写明“如何确认工作”，别只信“测试全过” {#qt03}
**作者/机构**：Anthropic（Claude Code 文档）｜**日期**：持续更新｜[原文](https://www.anthropic.com/engineering/claude-code-best-practices)

官方最佳实践建议在说明文件里写清楚本仓库确认工作的确切命令（测试、类型检查、lint、如何跑单个测试文件），以及“CI 会因什么失败”这类规则；提醒仅凭一句“All tests pass”信息量很少，读输出比重新跑检查更快；可以用只读子智能体对照 SPEC 评审 diff，检查每条需求是否实现、边界条件是否有测试。（此链接 v2 已收录，本专题从质量保障角度重读。）

> ““All tests pass” on its own tells you very little, and reading the output is faster than rerunning the check yourself.”

**证据类型**：厂商自报｜**对应原则**：[Q02](/handbook/12-quality-cicd#q02) [Q07](/handbook/12-quality-cicd#q07)

### QT04 · Claude Code Hooks：用 Stop hook 在“测试通过”之前不允许结束 {#qt04}
**作者/机构**：Anthropic（Claude Code 文档）｜**日期**：持续更新｜[原文](https://code.claude.com/docs/en/hooks-guide)

Hooks 文档给出了确定性保障的做法：PostToolUse 自动格式化；Stop 事件上挂“agent hook”，派生一个可读文件、跑命令的子智能体去核实测试是否通过，未通过则不允许 Claude 结束。适合把“完成的定义”从提示词变成机制。（此链接 v2 已收录，本专题从质量保障角度重读。）

> “Use agent hooks when you need to verify something against the actual state of the codebase.”

**证据类型**：厂商文档｜**对应原则**：[Q02](/handbook/12-quality-cicd#q02) [Q03](/handbook/12-quality-cicd#q03)

### QT05 · Claude Code GitHub Actions：在 PR 上自动评审，注意 fork PR 与密钥 {#qt05}
**作者/机构**：Anthropic（Claude Code 文档）｜**日期**：持续更新｜[原文](https://code.claude.com/docs/en/github-actions)

官方 GitHub Actions 集成：可在每个 PR 上自动评审（行内评论或汇总评论）、在 issue/PR 评论中 @claude 触发任务；评审标准写在仓库根目录的说明文件里。文档提示公共仓库中来自 fork 的 PR 拿不到 secrets，因此评审只在同仓分支的 PR 上运行；还需确认 CI 触发条件包含 Claude 推送产生的事件。

> “On public repositories, GitHub withholds secrets from runs triggered by fork pull requests, so the review runs only on pull requests from branches in the same repository.”

### QT07 · Anthropic：用 Claude + 属性测试在 100 多个 Python 包里找真 bug {#qt07}
**作者/机构**：Anthropic｜**日期**：2026-01-14｜[原文](https://www.anthropic.com/research/property-based-testing)

Anthropic 与合作者构建了自动编写属性测试（Hypothesis）的智能体：读代码和文档推断不变量，写 PBT、运行、反思并整理 bug 报告；在 100 多个流行 Python 包上发现了 NumPy 等项目的真实缺陷。文中记录了一个“自我纠错”细节：智能体发现自己把整个测试包在 try-catch 里，导致测试形同虚设。还另建了一个评估智能体复核 bug 报告的正确性与严重性。

> “However, after self-reflection, the agent realized that it had wrapped the whole test in a try-catch block.”

**证据类型**：厂商自报｜**对应原则**：[Q05](/handbook/12-quality-cicd#q05) [Q04](/handbook/12-quality-cicd#q04)

### QT08 · Agentic PBT 论文：智能体生成的 bug 报告 56% 有效 {#qt08}
**作者/机构**：Maaz 等（arXiv）｜**日期**：2025-10-10｜[原文](https://arxiv.org/abs/2510.09907)

上一条的论文版：LLM 智能体分析 Python 模块、从代码和文档推断函数级与跨函数性质、合成并执行属性测试。在 100 个流行包上评估，人工复核后 56% 的 bug 报告为有效 bug，32% 值得上报给维护者（论文自报）。属性测试给了智能体一个比“示例断言”更难糊弄的预言机。

> “Of the bug reports generated by the agent, we found after manual review that 56\\% were valid bugs and 32\\% were valid bugs that we would report to maintainers.”

**证据类型**：研究｜**对应原则**：[Q05](/handbook/12-quality-cicd#q05)

### QT09 · Hypothesis 官方 Claude Code 插件：先收集性质，再写测试 {#qt09}
**作者/机构**：Hypothesis 团队｜**日期**：2025｜[原文](https://hypothesis.works/articles/claude-code-plugin/)

Hypothesis 维护者发布 Claude Code 插件，用于在新仓库搭测试、扩充已有测试集或建立模糊测试流程。经验：让模型在写测试前后都充分收集“潜在性质”的上下文是高质量测试的关键；模型爱给生成策略加不必要的限制（例如限制列表最大长度），需要明确纠正。

> “For example, AI models like to write strategies with unnecessary restrictions, like limiting the maximum length of a list even when the property should hold for all lengths of lists.”

### QT11 · OpenAI：为 Codex 编写自定义评审规则——写不变量，lint 留给 CI {#qt11}
**作者/机构**：OpenAI Developers 博客｜**日期**：2026｜[原文](https://developers.openai.com/blog/custom-code-review-rules-for-codex)

官方经验：把评审者反复解释的检查（兼容性要求、数据边界、不安全副作用）写成简短、限定范围的规则，放在最靠近相关代码的 AGENTS.md；他们同时测试“应当被标记的违规”和“应当放过的改动”，以衡量规则的效果。格式与 lint 类问题留给 CI，评审规则只写需要判断的东西。

> “Encode a check reviewers repeatedly explain, such as a compatibility requirement or data boundary.”

### QT15 · GitHub：Copilot 云端智能体的风险与缓解——不能自批自合 {#qt15}
**作者/机构**：GitHub Docs｜**日期**：持续更新｜[原文](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)

GitHub 官方文档列出的内置护栏：Copilot 云端智能体不能把自己的 PR 标为 Ready for review，也不能批准或合并 PR；以自身应用身份开 PR 时，若仓库要求至少一个批准，则需要额外一次批准；触发任务的人也不能批准该 PR；智能体提交带签名、显示为 Verified；默认在有写权限的用户批准前不运行 Actions 工作流。

> “Copilot cloud agent cannot mark its pull requests as "Ready for review" and cannot approve or merge a pull request.”

**证据类型**：厂商文档｜**对应原则**：[Q03](/handbook/12-quality-cicd#q03) [Q09](/handbook/12-quality-cicd#q09) [Q13](/handbook/12-quality-cicd#q13)

### QT17 · GitHub Merge Queue：合并组在一起跑必需检查 {#qt17}
**作者/机构**：GitHub Docs｜**日期**：持续更新｜[原文](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

合并队列为排队的 PR 创建临时分支，把多个 PR 组合后一起跑必需检查，最后一个 PR 通过即代表整组变更通过；未报告必需状态检查则合并失败。智能体批量产出 PR 时，合并队列能避免“各自绿、合起来红”的语义冲突。

> “If the last pull request in the group has passed required checks, this means that the checks have passed for the combined set of changes in the merge group.”

**证据类型**：厂商文档｜**对应原则**：[Q11](/handbook/12-quality-cicd#q11) [Q03](/handbook/12-quality-cicd#q03)

### QT21 · Cursor：打造更好的 Bugbot——用“解决率”度量 AI 评审 {#qt21}

### QT23 · Cursor Bugbot Autofix：评审发现问题后由云端智能体在独立 VM 里修复并测试 {#qt23}

Bugbot 在评审中发现问题后，可派生在各自虚拟机中独立运行的云端智能体去测试软件并提出修复；Cursor 称超过 35% 的 Autofix 修改被合并进原 PR，解决率从 52% 提升到 76%（厂商自报）。评审与修复闭环，但修复仍以 PR 形式交人决定。

> “Bugbot Autofix spawns cloud agents that work independently in their own virtual machines to test your software.”
