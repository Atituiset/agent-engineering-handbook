# 关于

## 这是什么

一份关于「如何驾驭当前大模型与编码智能体」的中文实践手册，由两部分组成：

- **[原始报告](/sources/)**：从模型厂商、一线大厂、Thoughtworks、资深独立工程师、X、中文技术社区、开源项目与学术研究中整理的约 720 条精选资料（其中 X 帖子 255 条；含 2026-11 新增的质量与 CI/CD 专题，见 [质量与 CI/CD 专题](/sources/quality/)），每条附原文链接、中文摘要与证据性质标注。腾讯、阿里、字节的团队材料已按主题分散到各原始报告分类与手册章节。
- **[全量库](/library/)**：3,195 条资料的元数据（X 帖子 1,525 条、Hacker News 讨论 542 个、GitHub 仓库 630 个等），用来统计每条实践有多少独立作者支持、有多少异议，结果见 [共识度/佐证](/compare/evidence)。腾讯、阿里、字节相关条目带有公司字段，可在全量库筛选器中按公司查看。
- **[实践手册](/handbook/)**：在原始报告基础上提炼的 14 章方法论，外加一章可直接 clone 的落地起步套件（第 15 章），每章都与传统软件工程认知做对比，并说明选择理由。

## 为什么写

用智能体写代码一段时间后，很多有经验的工程师都有同一个感受：它很能干，却守不住团队的工程与架构约束。这份手册试图回答：一线团队是如何解决这个问题的？哪些经典工程认知依然有效，哪些需要修正？

## 方法与局限

- 精选条目的链接在 2026-11 实际打开核对；摘要忠于原文，引文逐字比对。全量库的 X、HN、GitHub 链接由各自官方 API 返回的数据生成。
- 共识度统计基于关键词自动归类，是粗略信号；「独立作者」按账号/域名/机构去重，同一人跨平台可能被重复计数。
- 大部分资料是厂商与个人的经验报告，真正的对照研究很少，且结论相互冲突。手册用「共识 / 分歧 / 待验证」标注证据强度。
- 章节结构：第 01–11 章与第 14 章统一为「要点 → 编号小节 → 2026-11 新证据 → 与传统认知的对比（含佐证列）→ 选择理由与证据强度」；第 12 章另有自己的 13 条质量原则（Q01–Q13）与共识度统计；第 13 章是清单型章节，对比表的佐证列多为「—」，因为它的新判断尚未纳入全量库统计。
- 范围：本手册只讨论**编码智能体**，不涉及客服、数据分析等其他类型的智能体。
- 这一领域变化极快，一些结论可能在下一代模型上失效。请把它当作一份带日期的快照，而不是定论。
- 若发现错误、失效链接或遗漏的重要来源，欢迎提 issue。
